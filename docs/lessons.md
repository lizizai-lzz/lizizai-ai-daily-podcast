# 实战沉淀：硬指标与踩坑表

来自 80+ 期真实节目的迭代记录。这些规则最初都是「翻车现场」，后来固化成了程序化校验或文档红线。

## 一、口播稿：AI 稿和真人播客的差距在哪

**结论先行：不在句长，在「有没有人在场」。** 2026-09 对标 12 段真实中文播客开头（`skills/ai-daily-podcast/references/voice-samples.md`）时发现：真实播客的人称词/问句密度远高于当时的 AI 稿，而平均句长本来就达标。所以主指标是人称与真问句，程序化为 `check_oral_voice.py`：

| 指标 | 阈值 | 翻车来源 |
| --- | --- | --- |
| 人称词（我/我们/你）/千字 | ≥ 20-25 | AI 稿默认「无人称陈述」 |
| 真问句/千字 | ≥ 2.5 | 问句是对话感的最低配置 |
| 书面连接词 | ≤ 2 | 「然而/与此同时/值得注意的是」 |
| 平均句长 | 8-18 字 | 太短像电报，太长念不动 |
| 语气词 | 2-5/千字（WARN） | **宁少勿滥** |

三条血泪教训：

1. **不要往专名和数字后塞语气词凑密度**——那正是 TTS 禁区（「Claude 呢」会怪到出戏）。
2. **不要把句子拆短当解法**——句长达标但内容密度崩了。
3. 语气词标准从「硬指标」降级为「软建议」（2026-10-13）：口语的主指标是人在场，语气词过量反而 AI 味。

### 语速标签禁令

`[放慢语速]` 一类标签全部禁用。原因：它们是给录音师的指令，TTS 会念出来或不稳定生效；节奏感应该由**标点与断句**承担——逗号轻顿、句号停顿、独立成段呼吸。

### 数字与单位是 TTS 第一杀手

实测最常翻车的写法（完整转换表见 SKILL.md Phase 2.6C）：

- `2024年` → TTS 念「两千零二十四年」→ 必须 `二零二四年`（逐位）
- `2亿` → 念「二亿」→ 量词前必须「两」
- `7/20` → 念「七杠二十」→ 必须 `7月20日`
- 英文单位（px/kg/$/%）必须汉化

## 二、双人播客：切人规范

每日精选是「一条新闻一位主持」的联播制：每个 `===` 区块由一位主持从事实讲到点评讲到过渡，另一位整条不出声（开场/收尾区块除外）。为什么这么严：

- 混播稿（一条新闻里 A/B 你一句我一句）听起来像自动生成的问答机，联播制才像真电台
- 程序化保障：`check_broadcast_speakers.py` 校验区块内只有一种前缀 + TTS 脚本合成前二次校验，双保险
- 重录效率：`--reuse` 按文本哈希缓存，改稿只重录变化的条目

## 三、ffmpeg 踩坑表（人物志流水线实测）

| # | 环节 | 症状 | 原因与修复 |
| --- | --- | --- | --- |
| 1 | SOT 剪切 | 中段切片输出**全静音**（max_volume -91dB） | `-ss` 放在 `-i` 之后（输出 seek）与 `loudnorm` 组合会丢失采样。**`-ss` 必须在 `-i` 之前**（输入 seek） |
| 2 | SOT 淡出 | 「话没说完就被减弱」 | 淡出起点 = 词级句尾 + **0.7s**（0.4s 都不够），时长 0.4s |
| 3 | SOT 切点 | 残留下一句开头的半句 | 下一句无空隙时（词级 end_time == 下一句 begin_time），切点 = 句尾本身；**绝不允许切在句中** |
| 4 | BGM 混音 | 尾奏在 17s 后消失 | `atrim` 保留源时间戳，`volume='if(lt(t,...))'` 包络的 t 从源偏移起算。**`atrim` 后必须加 `asetpts=PTS-STARTPTS`** |
| 5 | BGM 选曲 | 混入后几乎不可闻 | 曲目均值 -27dB 且稀疏。**先测电平**：`ffmpeg -i <bgm> -af volumedetect -f null -`，均值 < -25dB 或有长静音空洞的曲子不用 |
| 6 | BGM 时机 | 「太晚/没 BGM」 | 从片尾才起垫入太晚。从**正文收束段旁白**起垫，与片尾共用连续包络：淡入 1.5s → 0.125 压低 → 口播结束渐强 0.55 → 保持 4s → 3s 渐弱 |
| 7 | 跨段 BGM | 接缝处音量/旋律断层 | 收束段与片尾用**同一源文件的两个连续偏移**（`atrim=end=<vo13时长>` / `atrim=start=<vo13时长>`） |
| 8 | 转写依赖 | 系统 python3 跑不了听悟 | 缺 oss2：`pip install oss2` 或自建 venv |
| 9 | SOT 验证 | 静音空洞漏检 | 每段必做 `volumedetect`（> -30dB）+ `ffprobe` 时长；必要时把成品再转写一遍核对句子完整性 |

## 四、TTS 引擎选型记录

2026-09-28 试过本地 IndexTTS-2（Metal，RTF 2.57）对比火山引擎 API，最终不切换，三个硬伤值得记录：

1. **语速差 17%**（5.15 vs 4.39 字/秒）——全部字数密度标准都要重标
2. **英文术语发音不稳**——ASR 回读把 `HeyGen` 听成「黑」、`diff` 听成「di」，而科技稿英文词密
3. **情感控制语法不兼容**——本地模型走 emo 向量，与现有 `[情感标签]` 不是一套

> 结论：引擎选型是全链路耦合决策（字数标准、标签语法、发音质量），换引擎 = 重标定整条流水线。没有压倒性收益不要动。

## 五、发布侧

- 小宇宙对勾选「本音频为 AI 生成」的单集**强制进审核队列**，创作者侧无绕过入口，不要尝试取消勾选规避（违反平台规范）；审核期间公开链接 404 是 SPA 假象，看后台 `reviewStatus: PENDING`
- 上传脚本的三重验证（创建 API → URL → list 回读）：创建返回 200 但没 eid 不一定是失败，多是验证逻辑没回到列表页触发 list API
- 同天多集发布间隔 ≥4 小时；标题先查重防重复创建
- config.json 的时长/大小字段**永远由 finalize 脚本回填**，不要手工 `ls`/`ffprobe` 取值——人肉取值总有忘的时候，脚本化后此类错误归零

## 六、流程设计经验

1. **审计与内容分离**：知识库查询记录写独立 `knowledge_audit_{date}.md`，绝不写进脚本正文——否则审计文本会被 TTS 朗读出来（真实发生过）。
2. **渐进式披露**：三个栏目各有模块文件，生成哪栏只读哪栏——把三个栏目的文风规则同时塞进上下文，AI 会串味。
3. **去重是三维的**：项目级（任何已出现项目不得再选）、新闻级（标题实质相同不得再选，重大进展可做「故事线延续」）、主题级（7 天内 ≥2 次即饱和，同主题不再入选）。
4. **开头手法轮换**：每次交付把开头手法写进历史档案，下期必须避开近 7 天用过的——同一招用三天，听众就摸清你的套路了。
