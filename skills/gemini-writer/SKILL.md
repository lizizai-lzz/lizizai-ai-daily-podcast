# Gemini Writer

## Overview

基于 Google Gemini API（默认 `gemini-4-hydrogen`，Gemini 4 系列）的文章生成与编辑 Skill。完整流程：**收集需求 → 构造系统提示词 → 用户确认 → 提炼上下文 → 调用 Gemini → 落盘 markdown**。

本 Skill 不依赖任何第三方 Python 库，仅使用标准库 `urllib`，调用脚本为 `scripts/gemini_call.py`。

## 前置条件

- 用户已在 `~/.zshrc` 中 `export GEMINI_API_KEY='...'`。若调用脚本时检测不到 key，会以非零退出码报错，此时引导用户配置环境变量后重试。
- 系统已具备 Python 3（`python3` 可用）。

## 执行流程（必须严格按顺序）

整个流程分四个阶段，**禁止跳步**。每个阶段的产出必须可见、可被用户审阅。

### 阶段 1：构造系统提示词（System Prompt）

**目标**：按 `references/prompt_engineering.md` 的六大维度，生成一段完整、具体、可执行的中文系统提示词，并让用户确认。

**步骤**：

1. 读取并加载 `references/prompt_engineering.md` 到上下文（每次执行必读，规则权威）。
2. 解析用户当前对话中的需求，逐项尝试填充六大维度：
   - 角色 & 身份设定
   - 核心任务 & 目标
   - 目标受众
   - 语气 & 风格
   - 工作流 & 思考路径
   - 限制 & 红线
3. 对**无法从对话上下文明确推断**的维度，使用 `AskUserQuestion` 工具一次性询问（最多 4 个问题，单选 / 多选均可），禁止逐条追问。常见需询问的项：
   - 目标平台 / 受众人群（若用户未指定）
   - 字数区间（若未指定，可给出「短文 800 / 标准 1500 / 长文 3000」三档让用户选）
   - 语气调性（若用户只说「写一篇」未给风格）
4. 六维齐全后，组合成一段连贯中文自然语言段落（**不要带「维度 1：」这类标签**）。
5. 用**清晰的分组格式**把提示词展示给用户，请用户**确认或修改**。展示模板：

   ```markdown
   📝 已为你构造如下系统提示词，请确认：

   **【角色】**
   <内容>

   **【任务】**
   <内容>

   **【受众】**
   <内容>

   **【语气风格】**
   <内容>

   **【工作流】**
   1. <步骤 1>
   2. <步骤 2>
   ...

   **【限制红线】**
   - <限制 1>
   - <限制 2>
   ...

   如需调整，请直接告诉我修改点；确认无误回复「确认」即可。
   ```

6. 用户**未确认前**，禁止进入阶段 2。若用户要求修改，按修改点重写后再展示，直到确认。

### 阶段 2：提炼上下文（Context Assembly）

**目标**：按 `references/context_assembly.md` 规则，把用户全部有效输入组装成结构化文本块，作为 Gemini `contents.parts[0].text`。

**步骤**：

1. 读取并加载 `references/context_assembly.md`（每次执行必读）。
2. 从当前对话抽取：用户主请求、原始素材、关键约束、输出格式要求。
3. 若用户提到参考历史内容（如「按上次那篇的风格」），调用 `conversation_search` 抽取相关片段，作为素材的标注来源。
4. 若用户给了网页链接且需要 Gemini 参考，用 `WebFetch` 抓取摘要，连同原链接一起放进素材区。
5. 按固定分区模板组装：

   ```markdown
   # 任务

   <一句话>

   # 素材

   <原始素材原样保留>

   # 约束

   - 字数：<具体数值或「未指定」>
   - 平台：<具体平台或「未指定」>
   - 关键词：<列出或「无」>
   - 必须包含的元素：<列出或「无」>

   # 输出格式

   <markdown / 纯文本 / 标题层级 / emoji 规则>
   ```

6. 把组装好的上下文**展示给用户**简短确认（不需要像系统提示词那样严格审阅，只需让用户知道将传给 Gemini 的内容）。若用户无异议，进入阶段 3。

### 阶段 3：调用 Gemini

**目标**：通过脚本调用 Gemini，获取生成文本。

**步骤**：

1. 把阶段 1 的最终系统提示词写入临时文件 `<scratch>/system_prompt.txt`。
2. 把阶段 2 的最终上下文写入临时文件 `<scratch>/user_content.txt`。
   - **scratch 目录**：使用系统临时目录（如 `/tmp/gemini-writer-<timestamp>/`），不要污染项目目录。
3. 确定输出 markdown 路径。优先规则：
   - 用户明确指定路径 → 用用户路径。
   - 用户未指定 → 默认写到**当前项目目录**下的 `gemini-article-<YYYYMMDD-HHMMSS>.md`。
4. 执行：

   ```bash
   python3 <skill_dir>/scripts/gemini_call.py \
       --system <scratch>/system_prompt.txt \
       --content <scratch>/user_content.txt \
       --output <output_md_path> \
       --raw-json
   ```

   - `--raw-json` 建议带上，方便排错。
   - 退出码非 0 时，按脚本 stderr 的提示向用户解释原因并停止流程。
5. 脚本成功后，读取生成的 markdown 文件内容。

### 阶段 4：交付与后续

**步骤**：

1. 通过 `present_files` 把生成的 markdown 文件展示给用户。
2. 用一段简短中文总结本次产出（一两句即可，不要复述全文）。
3. 主动询问是否需要：
   - 微调（如「再短一点」「换个开头」「加一段数据」）—— 微调默认走「编辑模式」，重新构造上下文后再次调用 Gemini，参考 `编辑 / 续写模式` 小节。
   - 落盘到其它位置（如飞书 / 公众号草稿等其它 skill）。
4. 完成后按系统约定更新 memory。

## 编辑 / 续写模式

当用户的请求不是「新写一篇」而是「改写 / 续写 / 润色已有稿件」时：

1. **阶段 1 系统提示词**的「核心任务」维度改为对应的动词（改写 / 续写 / 润色），并在「限制红线」中明确「**保留原文风格 / 结构 / 关键信息**」或「**可大幅重构**」，由用户在确认时指定。
2. **阶段 2 上下文**的「素材」分区必须**原样包含完整原文**，不要摘要化。原文是 Gemini 改写时的唯一事实来源。
3. 在「任务」分区明确写出动作：`改写以下原文，使其适合 <平台>，目标 <业务目标>`。
4. 其余流程不变。

## 关键约束

- **严禁跳过用户确认**：阶段 1 的系统提示词必须经用户确认。确认前不得调用脚本。
- **严禁改写素材**：用户提供的素材即使在上下文阶段也要原样保留，禁止 WorkBuddy 自行精简或改写后传给 Gemini。
- **严禁凭空编造维度**：六大维度中无法推断的项必须问用户，不能默认。
- **API key 不写死**：脚本只从环境变量读 `GEMINI_API_KEY`，任何情况下都不把 key 写进 SKILL.md / 脚本 / 临时文件。
- **使用 ASCII 引号**：所有 shell 命令、文件路径、JSON 中的引号一律使用 ASCII 直引号（`"` / `'`）。
- **临时文件归临时目录**：`system_prompt.txt` / `user_content.txt` 等中间产物写到 `/tmp/`，**只有最终 markdown 才落到项目目录**。
- **模型可换**：默认 `gemini-4-hydrogen`（Gemini 4 系列轻量档，$1.5/$7.5 每百万 token）。可换 `gemini-4-neon`（高速档，文案更活，价格约 2 倍）、`gemini-4-argon` / `gemini-4-carbon`（旗舰档，贵），通过 `--model` 传入。
- **失败要解释**：脚本返回非 0 时，把 stderr 的中文提示原样转述给用户，不要静默重试。

## 资源清单

- `scripts/gemini_call.py` — 调用 Gemini `generateContent` 的 Python 脚本，使用标准库，无外部依赖。
- `references/prompt_engineering.md` — 系统提示词构造规则，阶段 1 必读。
- `references/context_assembly.md` — 上下文提炼规则，阶段 2 必读。
