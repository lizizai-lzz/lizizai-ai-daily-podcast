# 系统提示词构造规则（Prompt Engineering）

本文件是 `gemini-writer` skill 构造 Gemini `systemInstruction` 时的**唯一权威规则**。WorkBuddy 在向用户确认提示词前，必须按此文件的六个维度逐项填充。

## 总体原则

- 每一条系统提示词必须**完整覆盖六个维度**：角色、任务、受众、语气、工作流、限制。缺一不可。
- 描述需要**具体、可执行**，避免「你是优秀的写手」这类空话。要带可度量的特征（年限、行业、平台、风格特征词）。
- 凡是 WorkBuddy 自己**无法从对话上下文中确定**的维度，必须先用 `AskUserQuestion` 工具向用户询问，禁止自行编造。
- 最终生成的系统提示词必须以**纯文本**形式展示给用户**确认**，未确认前不得调用 Gemini。

## 六大维度

### 1. 角色与身份设定（Role & Persona）

明确 Agent 的专业背景、经验级别、看待问题的视角。这决定它的认知基准。

构造要点：
- 写出**具体年限**（如「10 年经验」），不要写「资深」。
- 写出**具体行业 / 平台 / 内容形态**（B2B 科技专栏、小红书种草、知乎长答、微信公众号深度文……）。
- 写出**代表性能力**（如「擅长把复杂商业逻辑翻译成故事」「精通 SEO 关键词布局」）。

示例：
> 你是一位拥有 10 年经验的资深 B2B 科技行业专栏作家，精通将复杂的商业逻辑转化为易懂的故事，长期为 36Kr、虎嗅供稿。

### 2. 核心任务与目标（Task & Objective）

清晰定义它需要完成什么，以及最终要达成的业务目标。

构造要点：
- 任务动词要具体：「撰写」「改写」「续写」「润色」「总结」。
- 业务目标要可观察：转化率、互动率、SEO 排名、阅读完成率、品牌专业感……
- 若是编辑任务，要写清是「结构性重写」还是「润色保留风格」。

示例：
> 你的任务是根据用户提供的主题与素材，撰写一篇 1500 字左右的微信公众号深度文章，目标是让读者读完后主动转发并关注公众号。

### 3. 目标受众（Target Audience）

描述内容是写给谁的。受众的年龄、职业、痛点、阅读习惯会直接影响深度与用词。

构造要点：
- 至少覆盖：年龄段、职业 / 身份、阅读场景（地铁、午休、睡前）、痛点 / 渴望。
- 给出**语言偏好**（专业术语、网感、口语、书面化）。

示例：
> 你的读者是 25–35 岁的一线城市互联网从业者，他们熟悉术语、时间碎片化、追求高效获取信息，反感啰嗦的开场和注水段落。

### 4. 语气与风格（Tone & Style）

规定语言调性与修辞偏好。

构造要点：
- 调性词至少给 2–3 个（专业且富有同理心、克制冷静、热血煽情……）。
- 明确**句式偏好**（短句优先 / 长句铺陈 / 口语化）。
- 明确**修辞偏好**（多比喻、多数据、多引用、多小标题）。
- 列出**禁用风格**（说教、网络烂梗、夸张极限词）。

示例：
> 语气专业但不学究，多用短句和小标题分隔节奏；可适度使用比喻但严禁网络烂梗；避免使用「全网第一」「封神」等夸张极限词。

### 5. 工作流与思考路径（Workflow & Chain of Thought）

引导 Agent 按步骤生成，避免上来就堆文字。

构造要点：
- 用 1./2./3. 编号明确**生成顺序**。
- 至少包含：素材整理 → 结构设计 → 内容填充 → 自检优化。
- 自检项要具体（SEO 关键词、字数、错别字、开头钩子、结尾 CTA）。

示例：
> 请按以下步骤工作：
> 1. 从用户提供的素材中提炼 3 个核心论点；
> 2. 给出文章大纲（小标题 + 每段主旨）；
> 3. 填充正文，保证每段不超过 4 行；
> 4. 自检：开头钩子是否抓人、结尾是否给出明确 CTA、是否出现禁用词。

### 6. 限制与红线（Constraints & Boundaries）

告诉 Agent 不能做什么，这是品牌安全和内容合规的关键。

构造要点：
- 内容红线：政治、宗教、医疗诊断、金融投资建议、未成年人敏感话题。
- 数据红线：禁止编造数据、引用必须有出处（或明确标注「示意」）。
- 措辞红线：极限词、绝对化表述、贬低竞品。
- 长度 / 格式红线：字数上下限、是否允许使用 emoji、是否需要 markdown。

示例：
> 严禁编造数据；不要使用「全网第一」「国家级」等极限词；不输出政治、宗教、医疗诊断相关内容；正文控制在 1500–2000 字，使用 markdown 格式，仅允许在标题层使用 emoji。

## 最终输出格式

六维写完后，组合成一段**连贯的中文自然语言段落**（不要带「维度 1：」这类标签），作为 `systemInstruction.parts[0].text` 的最终内容。展示给用户确认时，可用清晰的分组格式呈现，便于用户审阅。

## 决策树：维度信息从哪来

```
某个维度的内容是否可以从当前对话 + 用户历史偏好中明确推断？
├── 是 → 直接写入
└── 否 → 通过 AskUserQuestion 询问用户
        ├── 用户提供具体答案 → 写入
        └── 用户说「你看着办」/「用默认」 → 用本文件对应示例的稳妥默认值，并标注【默认】
```
