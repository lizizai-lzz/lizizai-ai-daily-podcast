# 上下文提炼规则（Context Assembly）

本文件说明 `gemini-writer` skill 在调用 Gemini 前如何**提炼并重构上下文**，作为 `contents.parts[0].text` 的最终内容。

## 核心理念

Gemini 接收的「上下文」= 用户的**全部有效输入**，而不是用户最近一句话。WorkBuddy 在调用脚本前，必须把以下信息汇总成一个**结构化文本块**：

1. **用户主请求**（原始任务的浓缩描述）
2. **用户提供的素材**（原文 / 草稿 / 资料 / 链接摘要）
3. **关键约束**（字数、平台、关键词、必须出现的元素）
4. **历史背景**（仅在与本次任务直接相关时才带上，避免噪音）
5. **明确的输出格式要求**（markdown、纯文本、是否需要标题层级）

## 输出格式

上下文用 markdown 结构化组织，固定使用以下分区：

```markdown
# 任务

<一句话描述本次需要 Gemini 产出什么>

# 素材

<用户提供的全部原始内容、资料、链接摘要；若有原文，原样保留；不要做改写>

# 约束

- 字数：<如未指定写「未指定」>
- 平台：<如未指定写「未指定」>
- 关键词：<列出，无则写「无」>
- 必须包含的元素：<列出，无则写「无」>

# 输出格式

<markdown / 纯文本 / 是否需要小标题层级 / 是否允许 emoji>
```

## 提炼规则

1. **不丢信息**：用户提供的素材即使冗长也要原样保留进「素材」分区，不要擅自删减。
2. **不做预判**：不要在上下文里替 Gemini 做判断（如「这里你应该强调 X」）。判断属于系统提示词的工作流，不属于上下文。
3. **去重噪音**：对话中的寒暄、确认句（「好的」「那就这么定」）不进入上下文。
4. **链接处理**：用户给的链接若需要 Gemini 参考，先用 `WebFetch` 抓取正文摘要，把摘要连同原链接一起放进素材区。
5. **历史背景**：默认不引入历史对话。只有当用户明确说「参考之前那篇的风格」之类时，才从 conversation_search 或 memory 中抽取相关片段，放进「素材」分区并注明来源。
6. **任务冲突**：若用户输入中存在矛盾（既要短又要详尽），不要自行调和，原样写进「约束」并标注「⚠️ 矛盾」，让用户在确认系统提示词时一并处理。

## 与系统提示词的边界

| 项目 | 属于系统提示词 | 属于上下文 |
|------|----------------|------------|
| 写作角色 | ✅ | ❌ |
| 风格语气 | ✅ | ❌ |
| 本次主题 | ❌ | ✅ |
| 具体素材 | ❌ | ✅ |
| 字数限制 | ❌（写「字数策略」） | ✅（写具体数值） |
| 输出格式 | ❌（写「通用格式偏好」） | ✅（写本次具体格式） |

简单记忆：**系统提示词管「怎么写」，上下文管「写什么」。**
