# 模块：开源解读

> **加载范围**：只在你负责生成「开源解读」这一条时完整读取本文件。共用流水线（Phase 0 知识库与去重、Phase 1 选题、Phase 2.5 config.json、Phase 2.6 后处理、Phase 3 音频与封面、Phase 4 交付）见 `../SKILL.md`。
> 本模块的产物：`script_opensource_{date}.md`（单人播报）。

## 播客定位

- **名称**：李自在AI日报 | 开源解读
- **时长**：8-10 分钟（5 个项目 × 约 1.5 分钟深度解读）
- **字数范围**：2000-2800 字（低于 2000 字每个项目讲不透，超过 2800 字音频过长）
- **格式**：单人深度解读，使用火山引擎 TTS 情感标签控制语调
- **受众**：所有对 AI 工具感兴趣的人——刚听说编码 Agent 的普通用户、技术型独立开发者、一人公司、超级个体（2026-11-24 放宽；写法上每个项目先给生活化类比或一句话定位让外行听懂，再讲机制与变现）
- **核心定位**：一个人在电台里给你拆解今天最值得关注的开源项目，重点是你能不能用它赚钱或提效；不预设听众认识任何项目

## 品牌口播（固定，每期必含）

开场品牌口播与收尾品牌口播是三条播客共用的，原文见 SKILL.md「品牌口播」。本模块只需要用下面这句交叉推荐：

> "今天的开源解读就到这里。想听今天的产品更新可以听**每日精选版**，行业格局和融资分析听**行业洞见版**。"

## 标题生成规则（开源解读专用）

开源解读播客的标题使用**「单项目标题法」**：从当天 5 个开源项目中评选出一个最具价值的，围绕它生成标题。**禁止使用"5 个值得关注的 AI 开源项目""今天这几个开源项目很能打"这类普适性、合集式标题**，这种标题放在任何一天都成立，完全失去当天内容的辨识度。

### 评选"最具价值项目"的五个维度

对 5 个候选项目逐一打分（每维度 0-2 分，满分 10 分），选**总分最高**的项目作为标题主角。若出现并列，按下面维度顺序的优先级打破平局。

| 维度 | 2 分 | 1 分 | 0 分 |
|------|------|------|------|
| **① 内容新鲜度** | 当天/近 24h 首次发布、首发版本、重大版本更新（v1.0、v2.0）、首次开源 | 近一周内已发布但今天有新增量（如新 plugin、新模型支持） | 已存在多日，今天只是再次上榜 |
| **② 上手容易度（部署门槛）** | 一行命令跑通 / pip install / npm 一键启动 / 提供 Docker 镜像和 hosted 版本 | 需要简单配置或少量依赖，文档清晰，30 分钟内可跑通 | 需要 GPU、需要复杂依赖、需要自建基础设施、文档不完善 |
| **③ 开源程度（License 友好度）** | MIT / Apache 2.0 / BSD（完全可商用，无任何限制） | MPL / LGPL / 自定义宽松协议（可商用但有少量义务，如保留署名） | AGPL / SSPL / 非商用协议 / 源码可见但非真正开源（商业使用受限） |
| **④ 独立开发者变现/提效价值** | 有明确可验证的变现路径或能替代付费工具（省下月费/人力成本） | 能明显提效但变现路径需要自己探索 | 偏研究性质、demo 性质，短期难落地 |
| **⑤ 差异化（vs 同类）** | 做法与同类完全不同（如更轻、更快、更便宜、新范式） | 与同类有差异但不显著 | 同质化，无明显优势 |

> **维度选取理由**：①新鲜度决定"为什么今天讲它"；②上手度决定"听众听完会不会去试"；③开源程度决定"能不能拿来做生意"；④变现价值是独立开发者最关心的；⑤差异化决定它值不值得被记住。五维同时考虑，避免单一维度（如只看 Star 数）选出不具实际价值的项目。

### 评选流程（写入 topic_selection 文件的开源解读章节）

1. 对 5 个项目逐一打分，生成一个简短的打分表（项目名 | ①新鲜度 | ②上手度 | ③开源度 | ④变现价值 | ⑤差异化 | 总分 | 一句话理由）
2. 选出总分最高的项目，记为"标题主角"
3. 在 topic_selection 文件中明确记录："**今日标题主角项目：{项目名}（{总分}/10）{一句话价值判断}**"
4. 若最高分 ≤ 4 分（即整体价值不高），仍然按规则选最高分项目，但标题中需要诚实反映其局限（见下方"诚实性约束"）

### 围绕"标题主角项目"生成标题

选出主角项目后，按以下规则生成标题：

**字数**：15-20 字（信息完整优先于字数，与每日精选同口径）

**必须包含**：
- **项目名或项目的核心能力关键词（必须出现）**，最近几期反例：`53K 星的开源 AI 渗透测试`（丢项目名 strix）、`14 万星编码 Agent 强在哪`（丢项目名 claude-code）。丢项目名的标题，听众听完也不知道该去搜什么，辨识度直接归零
- 该项目区别于同类的"那一个亮点"（新鲜度 / 上手度 / 开源协议 / 变现价值 / 差异化 中的最突出的一项）

**亮点表述要具体可感**：避免口号式模糊表述。反例：`DeepSeek Harness：一切皆插件`（"一切皆插件"放哪个 Agent 框架都成立）；正例：`DeepSeek Harness：官方 Agent 运行时`（点明身份）或 `DeepSeek Harness：工具技能随意插拔`（点明能力）。

**标题结构模板**（从以下 6 种中选 1 种，不要每次选同一种）：

| 模板 | 结构 | 示例 |
|------|------|------|
| **项目名 + 核心价值** | {项目名/能力词} + {一句话价值} | "Ollama：一行命令跑本地大模型" |
| **反差对比** | 别的同类都 X，这个 Y | "别家 Agent 要云端，这个能跑在手机上" |
| **痛点直击** | {独立开发者痛点}，{项目如何解决} | "想本地部署 LLM？试 Langchain 替代品" |
| **数字冲击** | {一个有冲击力的数字或事实} + {项目名} | "三天涨两万 Star 的 OCR 新秀" |
| **场景化** | {具体使用场景}：{项目} | "独立开发者搞 RAG，这个库最快" |
| **趋势信号** | {一个新趋势/新范式} + {代表项目} | "MCP 生态新选手：MCP-Inspector" |

### 标题自检清单

- [ ] **辨识度检查**：把标题单独发给别人，对方能猜出是"今天"的内容吗？如果"放在一周前/一周后也成立"→ 标题失败，重写
- [ ] **项目明确**：标题里出现具体项目名或核心能力词了吗？（`53K 星的开源渗透测试工具` → 失败，必须点名 strix）
- [ ] **避免合集式**：标题里有没有"5 个""这几个""合集""盘点"等词？有 → 失败
- [ ] **避免空泛形容词**：有没有"值得关注""很能打""很强"等不传递信息的形容词？有 → 失败
- [ ] **字数**：15-20 字，信息完整优先（主体/动作/亮点齐全）

### 诚实性约束

- 如果当天 5 个项目整体价值都不高（最高分 ≤ 4 分），不要强行拔高。标题用"冷思考"姿态，如"这个开源项目火得有点早"
- 如果主角项目的开源协议有商用限制（维度③ 0 分），标题中需要暗示这一风险，如"功能强大但商用要三思的 XX"
- 如果主角项目部署门槛高（维度② 0 分），不要用"一行命令""快速上手"等字眼

### 封面图 hit1 的协同

开源解读的封面图 `hit1` 字段必须与标题主角项目一致，把该项目的核心价值浓缩到 ≤ 15 字，与标题形成呼应。`hit2`/`hit3` 可以从其余 4 个项目中选 2 个有代表性的。

## 内容范围与筛选标准

从选题判断结果中获取分配给开源解读的 **5 个开源项目**。

### 项目筛选硬标准

每个入选项目必须满足至少一项：
1. 独立开发者可以直接用来赚钱（可商用、有明确变现路径）
2. 独立开发者可以用来大幅提效（自动化、替代人工、降低成本）
3. 与一人公司/超级个体的工作流直接相关

不满足以上任何一项的项目不入选。

### 三栏通用内容排除

开源解读不选以下两类项目：

- **以 Agent 安全为核心**：主要用途是 Agent 沙箱、权限、身份、提示注入防护、工具或 Skill 投毒检测、越权防护、红队攻防。
- **以漏洞为核心**：主要用途是漏洞扫描、验证、复现、利用、披露或补丁管理。

一个综合工具如果核心价值不是这两类，只是附带安全或漏洞检查能力，仍可入选；隐私、监管、合规、诈骗、内容安全、可靠性、模型对齐等项目不自动排除。

### 跨天去重规则

- 查询知识库 `wiki/sources/` 中最近 3 天的 `daily-*.md` 日报页，确认项目是否曾在近 3 天的开源解读中出现过
- **同一项目 3 天内不得重复入选**（除非有重大版本更新或重大事件）
- 如果项目曾在之前出现过，脚本中应用"上次我们聊到 XX"的方式自然衔接，而不是假装第一次介绍

## 脚本格式：火山引擎 TTS 情感标签

开源解读使用单人 TTS 生成，脚本必须使用 `[情感描述] 文本` 格式控制语调和节奏。

### 情感标签池（扩容版）

**开场/引入**（选 1-2 个）：
- `[热情欢快地]` `[像在跟老朋友聊天似的]` `[好奇地]` `[像在翻一份惊喜包裹]`

**项目介绍/亮点**（选 2-3 个，不要重复）：
- `[兴奋地]` `[略带惊讶]` `[像发现了一个宝藏]` `[眼前一亮]` `[平静地]` `[认真分析地]`

**商业化/实用性分析**（选 1-2 个）：
- `[语气坚定地]` `[一针见血地]` `[像在做一笔精明的投资分析]` `[实用主义地]` `[坦诚地]`

**难点/风险提醒**（选 1 个）：
- `[略带遗憾地]` `[实话实说]` `[提醒你注意]` `[冷静地]`

**上手建议**（选 1 个）：
- `[鼓励地]` `[轻松地]` `[像老手给新手指路]`

**过渡**（选 1 个）：
- `[轻松自然地]` `[语调上扬]` `[像换了个话题]` `[收起笑容]`

**不要用** `[pause]` `[laugh]` `[gasp]` 等英文标签

### 标签使用规则

- **相邻两段不能用同一个标签**
- **全文同一个标签最多出现 3 次**
- `[轻松地]` 这个标签在三篇脚本中被过度使用，注意克制

## 每个项目的解读结构（多模板，不要每个项目用同一套）

### 5 种解读模板（每篇 5 个项目必须至少使用 3 种不同模板）

| 模板 | 适合的项目类型 | 结构 |
|------|--------------|------|
| **标准型** | 功能明确、有清晰商业路径的项目 | 定位 → 核心亮点 → 商业化场景 → 上手建议 |
| **痛点先行型** | 解决具体痛点的工具类项目 | 痛点场景 → 这个项目怎么解决的 → 跟同类对比 → 谁该用谁不该用 |
| **对比深挖型** | 有明确竞品、需要做选择的项目 | 跟同类项目的差异 → 适用场景分化 → 选它的理由 vs 不选它的理由 |
| **实战推演型** | 可以立即上手的小工具/API | 假设你今天就要用 → 从安装到出成果的完整路径 → 适合什么阶段的产品 |
| **冷思考型** | 热度很高但需要理性评估的项目 | 为什么它这么火 → 火的背后的真实价值 vs 水分 → 什么人适合入坑，什么人先观望 |

### 解读要求

- 每个项目必须聊出至少一个具体的赚钱或提效场景
- **可以质疑项目**："说实话，这个项目目前还比较早期""协议是 AGPL，商用要三思"
- **可以分享自己的判断**："如果让我选，我会把时间花在第三个项目上"
- 项目之间用逻辑关联自然过渡

### 商业化建议的诚实度要求（核心约束）

**禁止空想的"你可以构建一个 SaaS"式建议。** 这类建议没有信息量，听了等于没听。

**好的商业化建议**（至少满足一条）：
- 有具体的目标用户画像："适合给律师、医生这些隐私敏感行业做知识库"
- 有具体的收费模式和市场验证："类似产品在 ProductHunt 上月活超过十万"
- 有自己的真实经验或朋友案例："我朋友试过用它替代 XX，成本降了百分之七十"
- 诚实承认不确定性："这个方向能不能赚钱我现在也不确定，但技术趋势是明确的"

**坏的商业化建议**（禁止使用）：
- "你可以构建一个 XX SaaS"（没有目标用户、没有验证、没有具体场景）
- "按 XX 计费，客单价 XXX 元"（编造的数字）
- "市场需求是验证过的"（没有说谁验证的、在哪里验证的）

### 上手建议的诚实度要求

**不要每个项目都说"简单、快速、轻松"。** 真实的开源项目都有坑。

- **必须提到至少一个具体的难点或限制**（哪怕是简单的"需要 GPU""文档还不够完善""中文社区小"）
- **诚实地给出时间预估**：不是说每个都"30分钟跑通"，复杂的说"建议周末花半天"
- **可以说"不建议现在入坑"**：如果项目太早期，直接说"先 star 观望，等文档完善再试"

## 开头方式（每篇从以下 5 种手法中选 1 种，不要每次选同一种）

开源解读的开场必须紧扣"独立开发者的视角和需求"，不要用通用化的开场。以下 5 种写作手法是**生成开场口播的指引**，不是写好的成品话术：选定一种手法后，结合当天 5 个开源项目的具体内容生成对应的开场。

| 手法 | 说明 | 适用场景 | 示例 |
|------|------|---------|------|
| **痛点引入** | 描述一个独立开发者常见的痛点，让听众产生"对，我也遇到过"的共鸣 | 当天项目里有明显解决具体痛点的工具类项目 | "你有没有遇到过 Agent 的行为完全不可预测的问题？今天第一个项目就是冲着这个来的。" |
| **当日最强项目** | 直接抛出当天 GitHub Trending / Star 增长最猛的项目，用数据制造冲击 | 当天有明显热度冠军（24h Star 暴涨、首发即爆款）时优先 | "今天 GitHub Trending 上有个项目，一天拿了三千多 Star。我先说结论：值得关注，但别急着用。" |
| **趋势观察** | 从近期一周的开源生态趋势引入，把今天 5 个项目放进趋势里讲 | 当天多个项目属于同一赛道（如多个 Agent 框架、多个 RAG 工具） | "最近一周我发现一个趋势，Agent 框架突然百花齐放了。今天的五个项目里，有三个都跟 Agent 有关。" |
| **反直觉判断** | 先抛一个跟大众认知相反的判断（最火的可能最不值得看、热度高但协议有坑、冷门才是宝藏），制造悬念 | 当天有"Star 少但价值高""热度高但有协议风险""大厂项目不如社区项目"等反差时适合 | "今天五个项目里，Star 最多的那个先别急着装。最值得看的是排第三的，原因我后面讲。" |
| **独立开发者视角** | 直接从"如果你今天要做一个 AI 产品/省一笔 API 费/替掉一个付费工具"切入，把听众代入独立开发者身份 | 当天项目普遍跟独立开发者的日常工作流相关（编码、部署、监控、降本） | "如果你这周只有两小时折腾开源，今天这五个项目里，我建议你优先看第二个和第四个，一个能帮你省钱，一个能帮你省时间。" |

### 使用规则

1. **每期只选 1 种手法**，开场口播控制在 2-4 句话、不超过 80 字
2. **7 天轮换约束**：近 7 天内用过的手法不得重复，查 `podcast_history.md` 确认上一期开源解读用的是哪种手法，避开它
3. **手法选择依据**：由当天 5 个项目的特征决定（有痛点工具→选痛点引入；有热度冠军→选当日最强；多项目同赛道→选趋势观察；有反差→选反直觉；都跟独立开发者日常相关→选独立开发者视角）
4. **开场口播之后**：自然过渡到第一个项目的解读，不需要"我们来看第一个"这种机械引入

## 项目之间的过渡方式

### 过渡的核心原则

**不要假装所有项目都能串成一条线。** 5 个开源项目来自不同的开发者和团队，它们之间大概率不存在完美的逻辑链条。强行串联比坦诚跳转更让人不适，听众能感觉到你在表演逻辑。

### 三种过渡模式（按优先级排序）

| 模式 | 什么时候用 | 示例 |
|------|-----------|------|
| **真逻辑链** | 项目之间确实有上下游关系（需一句话说清怎么关联） | "第一个给了你 Agent 框架，但框架跑起来需要推理引擎，这就是第四个项目" |
| **对比转折** | 两个项目走了不同路线，或面向不同用户 | "上一个走的是全托管路线，绑定 GitHub。这个走的是相反的方向，完全本地化，数据不出你的机器" |
| **坦诚跳转** | 项目之间确实没有关联（这是最常见的情况） | "接下来换个方向""第三个是个轻量工具，第四个是个重量级框架""跟前面几个不太一样，接下来这个是做安全的" |

### 硬约束

- **每篇最多只有 1 对项目使用"真逻辑链"过渡**，其余必须用对比转折或坦诚跳转
- **禁止使用以下三个词**："恰好互补""正好互补""刚好是"，如果两个项目真的有关联，用一句话具体说明怎么关联（"第一个管通信，第二个管记忆，一个管说，一个管记"），不要用"恰好互补"一笔带过
- **禁止 5 个项目全部用同一种过渡方式**

### 好的过渡 vs 坏的过渡

```
❌ 坏："说到 Agent 协作，第二个项目恰好互补，Khoj，一个本地化 AI 助手"
   （Agent通信和本地化助手有什么互补关系？说不清就别说互补）

✅ 好："第一个解决的是 Agent 之间怎么对话。第二个解决的是另一个问题，Agent 怎么帮你记住东西。一个是通信层，一个是记忆层。"
   （说清楚了两个项目各自解决什么，不需要硬说它们"互补"）

❌ 坏："Agent 框架有了，AI 编码能力有了，第三个项目补上了企业级拼图"
   （"拼图"是万能胶水词，什么都能补上）

✅ 好："前两个分别解决框架和编码能力，但如果你要跑在生产环境，还缺一个东西，标准化的组件库。第三个就是。"
   （说清了缺什么、为什么缺）

❌ 坏："第四个项目叫 awesome-llm-apps"（无过渡，也无上下文）
✅ 好："前面三个都是要你花时间搭的东西。接下来这个反过来了，它帮你省时间。"
   （用"对比"做跳转，比无过渡好，比硬连自然）
```

## 收尾总结（反空洞）

### 三种"说了等于没说"的收尾（禁止使用）

1. **列举式总结**："从{项目1定位}到{项目2定位}到{项目3定位}...整个链条越来越完整"
   - 问题：你只是在重新念一遍项目名字，听众已经听过了
2. **万能趋势句**："基础设施层正在快速成熟 / 生态在完善 / 技术栈的拼图越来越完整"
   - 问题：这句话放在任何一天都成立，没有信息量
3. **万能建议句**："别再从零造轮子 / 把时间花在垂直场景上 / 技术门槛在降低"
   - 问题：这种建议不会改变任何人的行为

### 收尾必须回答一个问题

**"这 5 个项目放在一起看，告诉我了一个我之前不知道的事情是什么？"**

### 四种有效的收尾方式

| 类型 | 说明 | 示例 |
|------|------|------|
| **趋势判断型** | 5个项目共同指向一个具体方向 | "今天的5个项目放在一起看，我注意到一个信号，工具层不再是在增强AI的能力，而是在增强人对AI的掌控力" |
| **机会窗口型** | 指出一个具体的时间窗口 | "Agent框架赛道已经从'谁能做出最好的框架'变成'谁先被集成进最多的垂直场景'。如果你在做某个行业的Agent产品，现在是最好的入场时机" |
| **分化信号型** | 指出赛道正在分化成不同路线 | "今天的5个项目展示了Agent基础设施正在分化成两条路线，全托管的云端服务和全掌控的本地化部署。你得现在就想清楚站哪条线" |
| **反共识型** | 提出一个和大众认知相反的判断 | "大家都在关注Agent框架，但今天最值得注意的项目是GitHub Spec Kit，一个跟Agent无关的编码规范工具。因为当所有人都在追Agent时，先把需求说清楚的人反而跑得更快" |

### 收尾硬约束

- **禁止在总结段列举项目定位**（"从通信协议到隐私助手到编排框架"），听众已经听过了
- **必须给出一个判断句**，"我的判断是：{具体判断}"。这个判断要足够具体，以至于有人可能不同意你
- **行动建议要落到一个具体动作**，"如果你本周只有X小时，做{具体的事}"，而不是"关注XX方向"

### 为什么要有这一节

口语感应靠**人称、真问句、起句衔接**（"我/你/我们""那……""所以说""我关心的是"），**不靠堆语气词**。硬凑「啊/呢/吧/嘛/呀」到专有名词和事实句尾，火山 TTS 会把尾音念得很重，听感难受。

### TTS 语气词禁区（硬约束）

以下位置**禁止**加 啊 / 呢 / 吧 / 嘛 / 呀：

1. **专有名词后**（产品名、公司名、人名、型号、项目名）
2. **数字 / 评分 / 星数后**（如"五十三万星啊"）
3. **纯事实陈述句尾**

**允许**出现在：

- 真人会犹豫、缓和、确认的地方
- **真正问听众的问句**里（"那它适合谁呢？""具体要花多久呢？"）

同一段结尾不要连续堆多个语气词。

### TTS 干净稿规则（开源解读默认）

- **开源解读默认直接产出 TTS 干净稿**（流水线走火山 TTS，不另出"人读加语气词版"）。
- 进火山 TTS 前清掉专名 / 数字 / 纯事实句后的尾音；**保留**人称词与真问句。
- 不靠堆语气词硬凑密度；过检时语气词不足只 WARN，人称或问句不足才 FAIL。

### 三条写法（开源解读特有）

1. **每个项目先说"我和它的关系"**。样本里的主播都会交代自己为什么有资格聊这件事："因为我最近也写了一篇关于这个的文章，我自己现在在做 coding agent"（捕蛇者说）、"这是我自己这些年特别关心的一个话题"（三五环）。开源解读照做，但**不许编造亲测经历**，只能用真实可核查的关系：这个项目在日报里连续出现几天了、上周刚开源、头部客户覆盖过半、文档里怎么写。
2. **给判断，不给说明书**。每个项目的收尾要落到"你要不要用"上，用第二人称说清适用和不适用："你要是做音频相关的产品，这条值得留意""要是你想靠它做设计感很强的片子，它帮不了你"。这既是判断，也是人称密度的来源。
3. **卡点要具体、诚实**。样本敢说"我们号称硬核，但也没有什么干货"（内核恐慌）。开源解读的诚实不是客套，要落到动作上："那部分要走平台侧的审核，别急着给客户报工期""中文列名和日期格式要单独测"。
